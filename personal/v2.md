# Executor v2 beta (side by side with v1)

Runs upstream's `beta` image as a standalone container next to the v1 compose
deployment. It shares nothing with v1: its own container, volume, loopback
port, network, and public address.

|               | v1                                  | v2 beta                                               |
| ------------- | ----------------------------------- | ----------------------------------------------------- |
| Container     | `host-selfhost-executor-1`          | `executor-v2`                                         |
| Volume        | `host-selfhost_executor-data`       | `executor-v2-data`                                    |
| Loopback port | 4788                                | 4400                                                  |
| Address       | Tailscale Serve 8788 (tailnet only) | Cloudflare Tunnel, `https://executor.<zone>` (public) |

## Run

The app and its tunnel connector share a private Docker network, so the
connector reaches the app by container name.

```sh
docker network create executor-v2-net
docker pull ghcr.io/usefulsoftwareco/executor-selfhost:beta
docker run --detach --name executor-v2 --init --restart unless-stopped \
  --network executor-v2-net \
  --publish 127.0.0.1:4400:4400 \
  --volume executor-v2-data:/app/data \
  -e BETTER_AUTH_URL=https://executor.<zone> \
  -e EXECUTOR_DISABLE_ANALYTICS=1 \
  ghcr.io/usefulsoftwareco/executor-selfhost:beta
curl -fsS http://127.0.0.1:4400/health
```

`BETTER_AUTH_URL` must match the address opened in the browser. Session and
encryption keys are generated into the volume on first start.

## Public address

A named Cloudflare tunnel (`executor-v2`) publishes the app so hosted MCP
clients can connect. Its credentials and config live outside this repository in
`~/.cloudflared/executor-v2/` (`credentials.json`, `config.yml`).

```sh
cloudflared tunnel create executor-v2
# move ~/.cloudflared/<tunnel-id>.json to ~/.cloudflared/executor-v2/credentials.json
cloudflared tunnel route dns executor-v2 executor.<zone>
docker run --detach --name executor-v2-cloudflared --restart unless-stopped \
  --network executor-v2-net \
  --volume ~/.cloudflared/executor-v2:/etc/cloudflared:ro \
  cloudflare/cloudflared tunnel --no-autoupdate --config /etc/cloudflared/config.yml run
```

`config.yml`:

```yaml
tunnel: <tunnel-id>
credentials-file: /etc/cloudflared/credentials.json

ingress:
  - hostname: executor.<zone>
    service: http://executor-v2:4400
  - service: http_status:404
```

Rules that follow from being public:

- Create the owner account on a private address before publishing. The first
  person to finish setup becomes the owner.
- Do not put Cloudflare Access or a protected quick tunnel in front of it. Their
  email-PIN page is for browsers and blocks MCP clients' OAuth calls; a quick
  tunnel's random URL also cannot match `BETTER_AUTH_URL`. Executor's own
  sign-in is the gate, so use a long unique password.
- Leave `EXECUTOR_APPS_ALLOW_PRIVATE_FETCH` unset. Setting it to `true` lets
  every app in the instance reach the private network and this machine's local
  services; add it deliberately if an app needs that.

### n8n MCP and API endpoints

n8n runs on this machine's private network and Executor apps cannot reach
private addresses (`EXECUTOR_APPS_ALLOW_PRIVATE_FETCH` stays unset). The same
tunnel therefore publishes only n8n's MCP path on a second hostname. Match the
exact path: a prefix such as `^/mcp-server/` also serves n8n's editor HTML shell
for any other path beneath it. Add this
rule to `config.yml` above the catch-all, then route the name and restart the
connector:

```yaml
- hostname: n8n-mcp.<zone>
  path: ^/mcp-server/http$
  service: http://host.docker.internal:5678
- hostname: n8n-mcp.<zone>
  path: ^/api/v1/
  service: http://host.docker.internal:5678
```

The second rule publishes n8n's public REST API (spec at
`/api/v1/openapi.yml`, authenticated with an `X-N8N-API-KEY` header) so an
Executor app can manage workflows. An API key can create, change and delete
any workflow, so scope and rotate it accordingly.

```sh
cloudflared tunnel route dns executor-v2 n8n-mcp.<zone>
docker restart executor-v2-cloudflared
```

`https://n8n-mcp.<zone>/mcp-server/http` answers 401 without n8n's MCP token
and `/api/v1/*` answers 401 without an API key; every other path on that
hostname (editor, sign-in, internal `/rest` API, webhooks, health) returns 404
from the tunnel. The token and key are the only protection, so rotate them in
n8n if they leak. To remove: delete the rules, restart the connector,
and delete the `n8n-mcp` CNAME in the Cloudflare dashboard.

### Dashboard batch workaround (2.0.0-beta.10)

Behind any HTTPS proxy, beta.10 answers the dashboard's `POST
/api/dashboard/batch` with 403: it compares the browser's `Origin` with an
origin it derives as `http://<host>`. Pages then show "Unable to complete this
request". Until upstream fixes it, one Cloudflare Transform Rule on the zone
(Rules > Transform Rules > Modify Request Header, named "Executor dashboard
batch origin workaround") corrects the header for that route only:

```
(http.host eq "executor.<zone>" and http.request.method eq "POST"
 and http.request.uri.path eq "/api/dashboard/batch"
 and any(http.request.headers["origin"][*] eq "https://executor.<zone>"))
```

Action: set static header `Origin` to `http://executor.<zone>`. Requests from
any other origin still get 403. Delete the rule once a release fixes the check;
to confirm, this should return 400 without the rule:

```sh
curl -s -o /dev/null -w '%{http_code}\n' -X POST https://executor.<zone>/api/dashboard/batch \
  -H 'content-type: application/json' -H 'origin: https://executor.<zone>' -d '{}'
```

Record the running digest after each pull:

```sh
docker inspect --format '{{index .RepoDigests 0}}' ghcr.io/usefulsoftwareco/executor-selfhost:beta
```

## Upgrade

Stop, back up the volume, pull, replace the container, then re-run the
`docker run` command above. The tunnel container and DNS route stay in place.

```sh
docker stop executor-v2
docker run --rm -v executor-v2-data:/data -v "$PWD":/backup \
  busybox tar czf /backup/executor-v2-data-$(date +%F).tgz -C /data .
docker pull ghcr.io/usefulsoftwareco/executor-selfhost:beta
docker rm executor-v2
```

After every upgrade, re-check the dashboard batch workaround above. It is
temporary. Disable the Cloudflare rule and run the `curl` from that section: if
it returns 400, upstream has fixed the origin check, so delete the rule. Do not
leave it on after a fix. A corrected server will expect the real `https://`
origin, and the rule would then cause the same 403 errors it currently prevents.
If dashboard pages start failing right after an upgrade, the rule is the first
thing to remove.

The backup holds the generated keys, so treat it as a secret. To roll back,
restore the archive into the volume and run the previous image by digest.

## Remove

```sh
docker rm -f executor-v2-cloudflared executor-v2
cloudflared tunnel delete executor-v2   # then remove the executor CNAME in the Cloudflare dashboard
```

The `executor-v2-data` volume is left behind on purpose.
